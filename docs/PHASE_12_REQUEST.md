## 二、运营 Dashboard

在 WordPress 原生后台完善工作概览，帮助管理员决定下一步处理什么。

展示实际可获得的：
- 待处理投稿。
- 需要补充资料的投稿。
- 待审核社区评价及评价修订。
- 待处理举报和 Skill 纠错。
- 待审核作者认领。
- GitHub 扫描异常、扫描不完整及待核查来源。
- AI 草稿待审、失败或结果不确定任务。
- 邮件投递异常。
- 注册、验证及公开资源概况。

要求：
- 每个数字有清楚的统计范围，并能进入对应列表。
- 区分内容数量、任务数量、用户数量，不能混算。
- 显示统计更新时间、时区及必要的时间范围。
- 无数据、功能未配置、数据暂不可用必须区别展示。
- 不使用演示数字或静态假图表。
- 按实际权限展示数据和操作，不仅隐藏菜单。

## 三、用户运营管理

复用 WordPress Users 和 Phase 8 账户状态，不创建第二套用户系统。

完善：
- 用户列表中的邮箱验证状态、业务账户状态及注册时间。
- 本人投稿、评价、收藏等必要汇总。
- 按权限查看用户相关的处理记录。
- 暂停或恢复社区操作资格。
- 记录操作原因、操作者、时间及恢复条件。
- 数据导出、删除请求的处理入口。

安全要求：
- 业务账户状态与 WordPress 角色分开。
- 暂停账户不能通过其他入口继续投稿、评价或执行受限操作。
- 恢复账户不能自动发布此前被拒绝或隐藏的内容。
- 用户状态变化后，按既定规则处理公开评价、统计和缓存。
- 普通运营人员不能修改管理员角色、授予高权限或读取 API Key。
- 不能因新增验证规则锁住既有管理员。
- 用户数据导出和删除继续复用已有隐私机制，不另建不受控制的下载接口。

## 四、统一待处理工作台

整合已有审核入口，提供筛选、分页、等待时长、处理记录和下一步操作。

覆盖：
- 用户投稿。
- 社区评价与修订。
- 评价举报。
- Skill 纠错。
- 作者认领。
- 版本更新建议。

明确区分：
1. Skill 内容发布审核。
2. AI 草稿审稿。
3. 社区用户评价审核。
4. 投稿、认领和纠错处理。

统一工作台只整合入口，不合并或改写这些业务的状态机。

要求：
- 所有操作调用已有业务服务，不从后台列表直接写数据库绕过规则。
- 接受投稿不等于发布 Skill。
- 作者认领不等于授予编辑或发布权限。
- 审核评价必须针对具体修订，拒绝过期操作。
- 内部处理备注与用户可见反馈分开。
- 批量操作逐项验权并报告成功、失败及原因。
- 批量通过不能跳过人工审核或公开发布条件。

## 五、站内通知与邮件运营

复用 Phase 8 已有的站内通知和 notification outbox，以及后续阶段已有的业务事件。

### 站内通知

完善：
- 我的通知列表和分页。
- 未读数量。
- 单条及批量标记已读。
- 合理的通知类型筛选。
- 本人通知偏好。
- 关联目标不可用时的安全提示。

所有读取、修改和跳转都检查当前用户及目标权限。

不能通过通知标题、快照或链接泄露已撤回内容、他人投稿、举报人身份或内部备注。

### 邮件运营后台

提供：
- 模板及中英文预览。
- 队列、尝试、传输受理、失败和结果不确定状态。
- 固定错误码及脱敏说明。
- 有限重试、暂停和到期处理。
- 必要的配置诊断与发送统计。

要求：
- 沿用已有状态机和幂等规则，不另建邮件队列。
- 业务处理成功而发信失败时，只重试通知，不能重复审核、创建资源或改变业务状态。
- wp_mail 返回成功不能显示为“用户已收到”。
- 没有可靠回执时，不计算或展示虚假的送达率。
- 不确定发送结果必须明确标识，不能无限重试。
- 不在日志、模板预览或后台页面暴露验证链接、Token、密码或密钥。
- 不自行实现不安全的密钥存储或降低既有加密保护。
- 真实发送只面向明确授权的测试收件人。
- 不新增营销群发、周精选订阅或自动导入会员邮箱；这些属于后续阶段。
- 不自动开启此前暂停的 AI 或采集任务。

## 六、运营统计与指标口径

复用 Phase 9、11 的真实事件和日聚合，不重新创建统计主存储。

逐项提供有实际数据来源的：
- 新注册用户。
- 完成邮箱验证的用户。
- 活跃用户。
- Skills 有效浏览。
- 当前有效收藏。
- 当前有效、已审核评价。
- 投稿数量及处理结果。
- 投稿处理时长。
- 搜索次数和无结果搜索。
- 热门分类、场景和资源。

在文档和界面中定义：
- 指标名称。
- 数据来源。
- 时间范围与时区。
- 去重规则。
- 分子、分母和过滤条件。
- 数据采集起点。
- 更新延迟和已知限制。

重要规则：
- 不把注册人数当活跃人数。
- 不把 HTTP 请求量当有效浏览量。
- 不把每日去重人数简单相加后称为月度独立用户。
- 不把不同时间范围的投稿、审核数相除后称为准确转化率。
- 不回填未经记录的历史浏览、搜索或用户行为。
- 统计失败不能阻断正常浏览、搜索和提交。
- 测试数据与正式统计隔离。
- 不宣称反机器人或反刷机制能够识别全部异常流量。

## 七、搜索无结果分析与隐私

在已有搜索上补齐必要的运营分析，不改造为个人搜索历史系统。

要求：
- 区分真正零结果、查询失败和参数无效。
- 限制查询词长度及可保存内容。
- 排除或脱敏可能包含邮箱、Token、密钥等敏感信息的查询。
- 对低频查询采取抑制或不保留策略。
- 不保存原始 IP、完整请求 URL、完整 User-Agent 或不必要的个人轨迹。
- 明确事件和聚合数据保留期限及清理机制。
- 只向授权运营人员提供必要汇总，不公开原始分析接口。

运营人员应能据此发现需要补充的内容，而不是查看某个用户搜索过什么。

## 八、资源健康与失效处理

优先复用现有 GitHub 采集状态、imports、jobs 和日志。

后台区分：
- 来源正常。
- 扫描未完成。
- 请求失败或限流。
- 来源疑似缺失。
- 需要人工核实。
- 已处理。

要求：
- 不把一次超时或不完整扫描当作永久失效。
- 不自动删除 Skill、版本和人工译文。
- 不因错误状态直接改变已核实作者关系。
- 提供查看证据、重试及记录处理结果的入口。
- 外部链接检查如确有需要，必须异步、有界并限制请求目标。
- 继续执行 HTTPS、域名、重定向、响应大小、超时和频率保护。
- 不能根据用户任意提交的 URL 直接发起服务器请求。
- 不在普通页面请求中运行长时间巡检。
