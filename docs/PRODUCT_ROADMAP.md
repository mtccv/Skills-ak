## 1. 产品方向与不变的架构

V2 从双语 Skills 目录扩展为可注册、收藏、评价、投稿和持续发现资源的免费产品。前期不接支付、不建立订单/交易/付费订阅、不设置付费墙；赞助和未来会员能力只作清楚标识的运营配置及权限扩展。

用户已确定的决策：

- 账户完全使用 WordPress 原生 Users、角色、会话、密码和重置机制，默认注册角色为 `Subscriber`；支持邮箱注册、邮箱验证、邮箱登录及找回密码。不建立另一套账户、密码或会话表。
- 评价采用 1–5 整数星级，加真实评论、使用体验、可选优点/缺点；同一 `user_id + skill_id` 只有一份有效评价。未审核的新评价及编辑稿不计公开评分。
- 新 Skill 投稿只允许已注册且邮箱已验证的用户；由管理员审核。投稿受理、编辑审核、Skill 发布是不同状态，任何用户入口均不能直接发布。
- 保留 WordPress 原生后台、原创主题、内置 Core、PHP 8.3+、MySQL、Tailwind、Alpine；沿用 ModuleLoader、DAL、Migrator 和服务边界。业务不写进 `functions.php`，不建立独立管理 SPA。
- `skills.id` 永久稳定；中英文共用同一 Skill ID；`repository_id + source_path` 完整唯一键不变；不建立 Skills CPT 或第二套仓库/翻译主存储。原十四表、人工内容、不可变来源及 AI 历史全部保留。
- 公开查询继续经过 PublicCatalog：已发布、当前修订批准、有效审核证据和当前语言完整译文。收藏卡片、评价目标、排行、集合、作者页、通知跳转及 Sitemap 都不能绕过此门禁。

现有真实能力与新增能力边界：

| 现有基线 | V2 扩展 |
| --- | --- |
| `/zh/`、`/en/`；公开目录/搜索/详情、教程、说明页 | 复用 Router、View、Strings、SEO 和原模板组件添加账户及发现入口 |
| 原生 `aish_message` 私有 Contact/Submit，历史 `post_author=0` | 新投稿绑定当前 WP 用户，增加状态、修订、去重和处理结果；不按邮箱自动认领历史匿名投稿 |
| 原 Reviews 是 Skill 内容发布审核 | 社区评价建立独立服务与管理入口，不混用内容发布审核或 AI `ai_reviews` |
| `newest/oldest/title`，精选 `featured`、平台 `platform-*`、分类/标签 related | 增加真实浏览/收藏/评分排行、集合与场景；现有更新时间排序不能冒充热门 |
| 无前台账户、收藏、社区评分、通知或邮件发送 | Phase 8–12 分阶段实现，不能将导航占位、Mock 邮件或空表声明为完成 |
| Final QA 25 工作包：20 通过、0 失败、5 未执行 | 新功能需新证据；真实 WPML、GitHub、OpenAI、兼容 Provider、生成质量/账单五项未执行继续保留 |

### 2.1 必须前置的基础能力

1. **身份先于个人数据。** P8 建立登录、验证状态及“当前用户只能操作自己的对象”的共同规则。P9/P10 才接入收藏、评价和投稿实际服务；P8 Dashboard 不查询不存在的表，不展示虚构数量或可提交的假表单。
2. **事务通知先于运营中心。** P8 必须有验证/重置邮件、模板语言、队列状态、幂等、限频、失败与重发边界，以及账户通知的最低实现。P9/P10 复用它发真实事件；P12 才提供聚合管理、筛选、模板配置和运营诊断。`wp_mail()` 返回成功仅表示传输层接受，不等于收件箱送达。
3. **数据积累先于排行。** P9 最迟接入公开详情浏览的去重记录/日聚合，收藏状态及已批准评价事件；P11 才能发布 Views/Trending。P12 添加统计看板和搜索运营维度，不能成为 P11 首次采集的前置死结。历史数据从上线时开始，不能补造历史访问量。
4. **状态变更先持久化，再通知。** 业务事务以实际提交结果为准；通知事件/outbox 用唯一事件键去重，失败可恢复。邮件失败不撤销已成功收藏/投稿/审核，也不能把数据库失败显示成提交成功；未知邮件发送结果不盲目无限重发。
5. **营销许可独立。** 注册、邮箱验证、重置、审核结果和账户安全消息是事务用途；P14 周精选是单独自愿订阅，默认关闭，单独确认/退订。`Subscriber` 是 WordPress 角色名，不表示同意营销邮件。
6. **历史未知保持未知。** 旧匿名投稿不自动绑定新账户；P8 不提前改写既有匿名 Submit，P10 才切换为注册验证投稿，各开发阶段不等于完整 V2 已上线。旧账号不凭存在即宣称已验证邮箱，旧 Skill 的创建时间不假称首次发布时间，旧 SHA 不假称当前审核源码，旧浏览量不回填。

## 3. Phase 8：账户、资料与个人中心

**目标与交付：** 使用站点原有 WordPress 账户完成邮箱注册、验证、登录、退出、重置和资料维护，形成真实可用的个人中心。此阶段只开放已实现的账户及账户通知功能。

### 具体任务

- P8-01 定义 Accounts 服务，调用原生 `wp_insert_user`、认证、认证 Cookie/会话和密码重置 API；前台接受邮箱登录。保留 WordPress 管理员正常原生登录/恢复通道，不改写核心密码算法。注册明确创建 Subscriber，忽略客户端提交的角色/capability，避免继承误配置的高权限默认角色。
- P8-02 注册收集邮箱、密码、显示昵称、界面语言及必要政策确认；内部登录名由服务器生成，不将邮箱公开为昵称/作者 slug。邮箱唯一性校验与并发创建遵守统一锁/持久化策略；统一对外提示、限频、蜜罐、密码强度反馈与安全返回地址。
- P8-03 注册后发送一次性邮箱验证；令牌只存哈希、绑定用户/用途/目标邮箱、短期过期、单次消费，重发使旧令牌失效。未验证账户只可查看验证提示、重发、退出和恢复，不可执行后续收藏/评价/投稿/认领。现有管理员会话和账号不因迁移被批量锁死；旧普通账户需明确验证状态，缺证据时要求完成验证后参与互动。
- P8-04 邮箱找回与重置复用 WP 原生 token/过期/消费规则，验证令牌不能兼作密码重置凭证。链接落地后移除 URL 中的敏感参数，禁止进入公开分析、引用来源、日志或共享缓存。修改密码/邮箱需近期认证；邮箱变更先验证新地址再替换，并处理旧会话、旧令牌及通知。
- P8-05 资料页维护显示名、简短介绍、界面语言、允许公开的站点链接及头像。邮箱默认仅本人/授权管理员可见；不默认开放公开用户目录。头像采用受控本地图片附件或默认图形，限制真实 MIME、像素、文件大小与所有权，重编码后使用；不赋予 Subscriber 通用 `upload_files`，不接受 SVG、可执行文件或任意远程抓取 URL。
- P8-06 Dashboard 显示真实验证/资料状态、账户通知和快捷入口。收藏、我的投稿、我的评价入口标注“功能尚未开放”或暂不出现；不向产品用户显示开发阶段编号，不显示假的零条历史、演示记录、成功交互或未经实现的增删功能。P9/P10 实现后替换为真实读模型。
- P8-07 最小 Notifications：验证、重置、安全变更等事务模板，中英两种真实文案，受限邮件 outbox/有界 worker、幂等事件键、失败/重试/过期状态与本人账户通知。重置仍由 WP 生成/校验凭证，不能建立第二套重置或账户系统；敏感 token 不进入长期可读通知正文。
- P8-08 提供隐私说明与 WP 个人数据导出/擦除 hooks；覆盖资料、头像、验证状态、短期令牌和通知。明确保留期限、用户申请入口及人工处理结果；删除/匿名化不能误删原 Skills、来源/AI 历史或其他用户资料。更新已实现功能对应的权限、审计和帮助说明。

**模块与数据：** 规划 Accounts、Notifications 模块及其 Core 服务；复用 Language、Frontend/Router/Strings、Admin、Security、Database。账户/角色/会话仍由 WP Users/usermeta 管理，资料/偏好用受限 usermeta，头像用 WP attachment；验证记录与事务 outbox 的新增结构按 [数据库设计](PRODUCT_DATABASE_DESIGN.md) 的 P8 定义迁移，不创建账户表。

**URL：** `/{lang}/register/`、`login/`、`verify-email/`、`forgot-password/`、`reset-password/`、`account/`、`account/profile/`、`account/security/`、`account/privacy/`、`account/notifications/`。注册验证/重置结果、全部账户页均 `noindex/nofollow/noarchive`、`private/no-store`、不进 Sitemap；这些计划路由在实现前不得作为可用地址宣传。退出和资料写入只接受 POST；受控 PRG 重定向保持原语言。

**角色/权限/安全：** 访客只有注册/登录/重置的受限入口；未验证用户只可验证和维护必要安全信息；已验证 Subscriber 操作本人账户。用户管理沿 WP `list_users/edit_users` 等能力并增加业务权限校验，普通用户永远不得赋权、读取别人的邮箱或访问 Core 管理服务。每次写入同时校验方法、nonce、当前用户、对象所有权和状态；nonce 不代替身份，密码/会话/令牌不进入日志或分析。

**多语言与依赖：** 依赖既有内置语言、Router 和原生 Users API。账户是跨语言同一用户，切换语言不建立新账户；界面与邮件分别使用用户选择的 locale，没有内容时不伪造译文。真实邮件送达和 WPML 适配分别记录；缺授权包时 WPML 仍为未执行。

**可验证验收：** 两种语言各完成注册→验证→邮箱登录→改资料/头像→退出→重置→重新登录；重复邮箱并发只产生一个账户；过期/重放/错误用途/旧邮箱 token 拒绝；恶意 redirect 不离站；未验证用户及另一账户越权失败；Subscriber 无后台管理/上传通用能力。验证信失效、队列失败与 `wp_mail` 接受分别展示真实状态。Dashboard 后续入口不冒充已实现。隐私导出只含本人资料，擦除不破坏 Skill/他人数据；主题切换保留账号和通知数据。

**开发检查：** 在获准实施时先审查原生认证与插件 hook 顺序、对象权限及 token 生命周期；做 PHP 8.3/8.4 语法、相关身份/令牌合同检查、前端构建及差异检查。真实 WordPress/MySQL 验证邮件、会话、重置、头像及并发单独取证；真实 SMTP/收件箱尚不可用时明确标为未执行，不以 Mock 邮箱截图证明送达。

## 4. Phase 9：收藏、评价、举报与最低统计

**目标与交付：** 注册用户可保存感兴趣的 Skill、留下可审核的使用反馈，并能管理自己的内容；公开评分由批准的真实评价组成。为 P11 提前建立最低可信浏览和互动计量。

### 具体任务

- P9-01 在卡片/详情添加收藏与取消收藏，个人中心提供搜索/分页/状态提示；状态来自服务器，唯一 `user_id + skill_id`，重复点击与重试幂等。取消仅停止该关系生效，恢复复用同一行并保留首次收藏时间，不能通过取消/重加刷新热榜时效；隐私擦除可删除该用户关系。收藏目标须当前可公开，撤下后个人收藏显示“暂不可用”及取消入口，不泄露草稿标题/内容；默认不公开个人收藏列表。
- P9-02 评价表单包含必填 1–5 整数星级、评论和实际使用体验，可选优点/缺点，记录原文语言；平台/场景描述可写在体验中，不冒充已核实的兼容标签。明示社区规范，禁止匿名评分；保存为待审核。避免再创建一套无星级平行评论系统，评论/体验是同一评价的组成部分。
- P9-03 一位用户对同一 Skill 只维护一个评价实体，修订独立保存；已批准版本和待审编辑稿隔离。编辑时公开页和分数继续引用仍有效的旧批准版本，待审新稿不计分；批准后原子替换，拒绝不覆盖旧版。用户撤回或管理员隐藏立即移除公开评论和分数；过期审核不能批准新的未看过版本。
- P9-04 管理员使用独立“用户评价”列表审核/拒绝/隐藏，记录原因、操作者、修订和时间；与原 Skills Reviews/AI Reviews 命名区分。评价编辑只能由作者或有审核能力的管理员完成明确的审核操作，不冒充作者写内容。
- P9-05 显示真实平均分、有效评价数量和星级分布；无批准评价显示“暂无评价”。评分聚合跨中英文共用 Skill ID，评论保留实际语言，可按语言筛选；语言筛选不能把总分误称当前语言总分。不生成虚构 AggregateRating 或将站点评分当安全认证。
- P9-06 支持举报评价及 Skill 纠错：选择类型、描述、证据链接，私有保存并回执；重复举报有唯一/限频保护，申报者只能看自己的状态和可公开处理答复，内部备注不外泄。管理员处理恶意反馈或争议，但不因举报自动删除/下架 Skill。
- P9-07 真实收藏/评价/举报状态事件接入 P8 通知基础，Dashboard 开放“我的收藏”“我的评价”；“我的投稿”仍保持 P10 未开放状态。只通知状态结果，不邮件抄送全部敏感举报或管理员内部备注。
- P9-08 接入公开 Skill 详情浏览的最低去重记录与按日聚合；排除后台预览、错误/重定向、爬虫及被撤回内容，来源和时间窗写清楚。同一计量身份对同一 Skill 在同一 UTC 日跨中英只计一次，不能把两种语言的分组简单相加；7/30 日统计是每日去重量累计，不称整个窗口独立访客数。收藏新增/取消和评价批准/撤回使用真实持久状态生成计量，重复请求/重试/反复切换不得叠加虚假热度。在短期事件保留窗口内支持日聚合对账/重建，窗口外保留已核对聚合及口径版本，不承诺恢复已删除明细；显示统计起始时间，不保存原始 IP、不建立跨站画像。
- P9-09 扩展 P8 隐私导出/擦除到收藏、评价、举报和统计：注销时移除有效收藏、公开评价指针和分数，必要审核证据去标识后按明确期限保留；不能用保留审计为由继续公开已撤回内容或恢复已删除账户的评分。

**模块与数据：** 新增 Community 服务（Favorites、Reviews、Moderation/Reports），Analytics 最小采集/聚合服务；复用 Accounts、Notifications、PublicCatalog 和原生后台。收藏、评价/修订、举报、操作事件及统计的表结构和索引按 [数据库设计](PRODUCT_DATABASE_DESIGN.md) 的 P9；所有记录引用既有 WP user_id 和稳定 skill_id，评论不进入 `skill_translations`。

**URL：** `/{lang}/account/favorites/`、`account/reviews/`、`account/reviews/{review_id}/`、`account/reports/`；公开评价嵌入现有 Skill 详情 `#reviews`，不为待审正文建立公开 URL。个人页、提交结果和筛选参数 noindex/no-store；写接口只接受 POST，服务再次校验所有权。

**角色/权限/安全：** 已验证 Subscriber 可管理本人收藏/评价/举报；仅审核人员可处理他人反馈，规划细分 `aish_moderate_reviews`、`aish_manage_reports`，默认管理员获得，原 `aish_review_skills` 不自动等于社区审核权。严格对象授权、修订号、数据库唯一键/事务、长度/富文本白名单、反刷和脱敏；公开显示昵称/头像经用户隐私选择，不公开邮箱。

**多语言与依赖：** 依赖 P8 认证、验证状态、通知与隐私 hooks；使用 P0–7 发布门禁。跨语言收藏去重，星级合并，原文评论不自动翻译。通知按用户偏好语言，审核理由以实际输入呈现；WPML 真实运行独立验收。

**可验证验收：** 两账户并发收藏/取消和重复请求计数一致；一用户同 Skill 跨语言只有一个收藏和评价；旧收藏取消重加不刷新热度时间。新待审评价为零公开贡献；5 星旧版编辑为 1 星待审时仍只计旧版一次，批准后改为 1 星，拒绝保留 5 星，撤回即时移除；过期审核/越权/伪造 user_id 被拒绝。举报、通知和公开分数可追溯到同一业务事件；撤下 Skill 不泄露详情。浏览刷新、重复事件、跨语言切换、worker 重放和跨午夜窗口按实际日窗口准确计量；明确显示统计开始时间，日去重累计不冒称窗口独立访客。

**开发检查：** 获准实施后做社区状态机/评分一致性/反刷与权限检查，PHP/构建和受影响旧查询回归；真实 MySQL 检查唯一约束、行锁、重放和聚合重建，真实浏览器检查登录前后/移动星级键盘操作及收藏撤回。统计结果核对输入事件清单，不能只断言 SQL 字符串。

## 5. Phase 10：注册投稿、开发者页与作者认领

**目标与交付：** 用户可提交可追踪的 Skill 建议，管理员在现有内容与来源流程中审核；开发者可以证明归属、展示经核验的公开资料并建议版本更新。

### 具体任务

- P10-01 将 `/submit/` 升级为已验证用户投稿：可选 GitHub 仓库根 URL、已知时填写的 `source_path`、建议名称/简介、原文语言、类别/平台建议、投稿说明；保留人工无 GitHub 来源的投稿。原始提交记录使用私有 `aish_message` 与 postmeta，服务器写入当前 WP 用户归属，不能由隐藏字段决定作者。
- P10-02 规范仓库 owner/name，已知相对路径严格验证并保持大小写、字节长度与完整值；保留用户提供 URL 作为证据，最终确认来源的唯一键仍是 repository_id + source_path。已知路径的既有 Skill、同用户未结案投稿和并发投稿按统一锁/幂等策略去重；未知路径保持 NULL/待确认，绝不默认成 `SKILL.md`。只有根 URL 时作为待发现的仓库线索受理，可最终关联多个 Skill，不能仅凭根 URL 合并或拒绝同仓库不同资源。无 GitHub 来源的人工投稿也不虚构仓库/path。
- P10-03 已确认路径且同源的公开资源提示现有详情；私有/待审同源资源只给通用“已记录/正在处理”提示，不能泄露标题、作者、审核备注。解析 URL 不触发前台 GitHub 请求或抓取任意域名；管理员授权使用原 Sources 服务发现未知路径，每个结果仍按规范来源独立去重并保持 pending。
- P10-04 用户可保存草稿、提交、查看待审/需补充/已拒绝/已采纳/已关联发布/已撤回等状态，在允许状态编辑或撤回；每次提交留修订，管理端只审核看到的版本。投稿撤回不删除已有 Skill，采纳只表示管理员建立或关联了记录，Skill 未通过正式审核前不能显示“已发布”。
- P10-05 管理员原生 Inbox 增加投稿筛选、差异/补充信息、重复关联、处理理由和通知动作；从投稿预填既有 Skills 草稿时明确选择字段，不能覆盖人工非空内容、slug/SEO 或自动发布。后台可将规范来源交给已有受限采集队列，仍保持 pending 和固定 SHA 安全规则。
- P10-06 作者认领提交可核验证据，记录用户、Skill、仓库/路径、声明身份、证据与审批；人工核验后建立“已验证作者/维护者”关系。GitHub owner 不自动等于作者，邮箱域名相同不构成所有权，禁止仅凭留言或昵称冒认。
- P10-06a 建议首版每 Skill 最多一个主要核实归属，区分作者与维护者角色；仓库控制只证明维护权，原创作者另须署名/授权证据，不能推断该 Skill 只有一位真实作者。转移/撤销在事务中处理旧关系并记录证据；其他贡献者可在正文中据实署名，不因此获得管理权。多人团队维护若进入范围须另定角色关系，不绕过唯一约束。
- P10-07 开发者/作者页展示用户选择公开的名称、简介、网站和批准的关联 Skills；未批准、撤销或缺少公开同意时不展示认领。认领只赋予提交更正/版本建议的业务资格，不授予 Skills 编辑、来源配置、AI 生成或发布能力。
- P10-08 版本更新建议引用已有 Skill、实际仓库路径/Commit/版本标签及变更说明，写入同一私有建议流程，管理员核实后使用已有 Sources/Management 处理。保存建议不会更改 `skill_versions`、审核修订、来源绑定或现有译文。所有结果使用 P8/P9 通知与事件记录。

**模块与数据：** Submissions、Authors 服务组装 Accounts/Notifications、Forms/NativeMetadata、Catalog/Management、Sources；投稿主体继续原生 posts/postmeta，保留所有历史匿名 Inbox，不建 submissions 或 Skills 影子表。author_claims 等关联按 [数据库设计](PRODUCT_DATABASE_DESIGN.md) 的 P10；投稿版本与状态审计、去重锁及与 Skill 的连接按同一设计维护。

**URL：** 复用 `/{lang}/submit/`；新增 `account/submissions/`、`account/submissions/{message_id}/`、`account/claims/`、`skills/{id}/{slug}/suggest-update/`、`authors/{public_handle}/`。作者公开 handle 不使用邮箱或内部登录名。私人记录、认领/建议/结果始终 noindex/no-store；作者页只有经同意公开且有实际当前语言内容与关联公开 Skill 时才能索引，缺译不造 hreflang。

**角色/权限/安全：** 投稿/认领须登录及邮箱验证；用户只能操作本人记录，历史匿名记录归属仍为空。规划 `aish_review_submissions`、`aish_manage_author_claims` 默认管理员；实际创建/编辑/批准 Skill 还须既有相应能力。敏感证据只供授权审核，任意 URL 不访问、不执行；审核和用户编辑竞争使用修订锁，重复请求不建立两个 Skill。

**多语言与依赖：** 依赖 P8/P9 的账户、通知/操作事件、P0–7 采集和人工审核。提交一份来源不自动生成两个 Skill 或伪造中英内容；开发者简介按实际语言维护，缺译页不输出假的替代关系。邮件用收件人的偏好语言，投稿原文保持原样。

**可验证验收：** 一个仓库的两个路径可分别投稿，已确认同源并发只能生成一个有效关联；大小写不同路径不误合并。未知路径保持 NULL，不猜成根 SKILL.md，仓库线索可由人工采集关联多个不同来源；无 GitHub 投稿能保存人工建议；匿名/未验证提交被拒绝；用户 A 无法查看/编辑/撤回 B 或历史匿名投稿。采纳但未发布的资源不出现在搜索/作者页/Sitemap；拒绝/补充/发布有真实可见状态和一次通知。旧修订审核、来源换绑、伪造认领拒绝；认领成功仍无法直接编辑/发布 Skill；版本建议不改变任何正式来源快照。

**开发检查：** 获准实施后检查原生 CPT 隐私出口、受限预填、所有权、状态机和来源规范化；运行 PHP/构建及既有 Inbox/采集/人工保护回归。真实 WordPress/MySQL 检查 posts/postmeta 事务、并发去重、审核竞争、邮件失败恢复及双语路由，外部 GitHub 身份核验无合法凭据时明确未执行。

## 6. Phase 11：发现、排行、专题与相关资源

**目标与交付：** 用实际内容、经过审核的用户反馈和有来源的统计帮助用户发现 Skills；每个榜单说明排序、时间窗和数据起始时间，不把编辑精选包装成自然热度。

### 具体任务与默认口径

| 功能 | 任务与可解释排序 |
| --- | --- |
| Trending | 使用 P9 已采集数据；默认近 7 个完整 UTC 日，依据每日去重浏览、真实新增收藏和首次批准评价计算有版本的分数，反复取消收藏/重审编辑不能重复加分；展示窗口、更新时刻、算法说明及数据不足状态 |
| Most Viewed | 依据合法公开详情浏览的日聚合排序；支持明确的 7/30 日窗口，结果是每天跨语言去重浏览量之和，不是整个窗口的独立访客数；不能用 GitHub Stars、页面 created_at 或伪浏览量代替 |
| Most Favorited | 使用当前有效收藏人数，已撤回收藏不计；支持全量当前快照，若提供期间新增榜则另行命名，不能混淆“存量”与“新增” |
| Top Rated | 仅当前有效批准修订；显示真实均分及评价数，默认至少 5 个有效评价才参加主榜；排序公式、最小样本和同分次序明确，样本不足显示尚无合格结果 |
| Recently Added | 按现有 `created_at` 表示“最近收录”，不得声称首次发布；若需首次上架展示，使用后续记录的实际首次批准事件，历史未知不回填成创建日 |
| Recently Updated | 按 `workflow_events` 中有证据的公开内容批准事件排序；来源 incoming、爬取任务完成、收藏和评论不能冒充正文更新；历史无对应事件时显示未知，旧 `newest` URL 兼容保留并说明原更新时间语义 |
| Editor's Picks | 复用人工 `featured`，扩展编辑理由、位置/有效期与按语言配置；只有被明确选中且当前公开的资源展示，不从榜单冒充精选 |
| Platform Collections | 复用 `platform-*` 标签作兼容依据，维护有标题/描述/顺序的编辑集合；平台未核实不展示兼容承诺，不复制 Skill 数据 |
| Use Cases | 建立可维护场景目录及中英真实说明，与现有 Skill ID 关联；正文中的使用场景仍保留，AI 仅建议、管理员批准关联；不把随机标签自动变成公开专题 |
| Related / Similar | 在既有分类/标签相关结果上加入已批准的场景/平台和人工相关关系，排除自身、重复和不可见资源；展示“共同分类/场景”等真实理由，不宣称已做 AI 语义验证 |

- P11-01 将以上列表接入统一 Discovery 查询服务，再经 PublicCatalog 批量获取当前语言公开卡片、计数与分页；榜单缓存只能存 ID/分数等派生结果，输出时重新过公开门禁，撤稿或审核失效不能等待缓存过期才隐藏。
- P11-02 为 Trending/评分/相关推荐确定明确算法版本、参数白名单和稳定同分次序（最终以 Skill ID 决定）。默认 Trending 拟采用每日 `ln(1 + V_d) + 3 × ln(1 + A_d) + 2 × ln(1 + R_d)`，最近完整日 `d=0`、最早 `d=6`，按 `2^(-d/3)` 加权汇总。`V_d` 来自 `daily_metrics` 的去重浏览；`A_d` 从 active 状态的 favorites 按不可被取消/恢复刷新、表示首次收藏的 created_at 分日取数；`R_d` 从当前有效 approved 指针的 reviews 按 first_published_at 分日取数，不读取运营用历史新增/撤回计数冒充当前有效信号。取消收藏、撤回/隐藏评价立即影响下一次排行；评价重发保留首次批准时间，反复收藏/取消仍只保留一份当前贡献，且不更新首次收藏日。上线前用可复算样本确认公式与查询一致；聚合无法核实时暂停相关排序并显示更新中。零有效信号不进入热榜，累计不足 7 日显示实际起始日，不推算缺失天数。Top Rated 默认先按均分、再评价数、再稳定 ID；不向稀少样本填默认满分。
- P11-03 榜单刷新用有界 Cron/派生聚合与明确更新时间，失败保留最后真实成功时间或显示不可用，不将空结果伪装当前成功。榜单不读取个人邮箱、评论私稿或私有收藏清单，不通过全量明细前台扫描求值。
- P11-04 集合和场景提供原生后台 CRUD、顺序、发布/归档、中英标题/slug/介绍/SEO、真实 Skill 关联；发布门禁校验集合本身及每张卡片。空集合、未发布、缺译或 noindex 不进入 Sitemap；缺译不复制另一语言正文。
- P11-05 首页分区可选择最新/精选/趋势/场景，但默认模块必须对应真实查询；没有数据时使用真实空状态。扩展搜索/筛选和排序参数白名单，旧链接保持可解析，参数页仍沿用 noindex 策略。
- P11-06 增加分类/标签名称与说明的真实中英维护，使用 `term_translations(term_type, term_id, locale)`，保留原 taxonomy ID、slug 和关联。缺译可显示原有共享名称并标明缺译，不据此宣称分类介绍已翻译；原有语言筛选/公开计数和 SEO 门禁继续生效。

**角色/权限/安全：** 用户仅看自身通知/偏好；规划 `aish_view_analytics`、`aish_manage_notifications`、`aish_manage_operations`，用户管理另需原生角色能力。默认管理员授予，运营编辑按明确授权分配；内部详情、批量动作、导出各自验权。服务级网络防 SSRF，管理员配置也不能访问内网/IP/任意重定向。

**可验证验收：** 每个运营计数能追到范围内真实业务记录；不同角色看到的菜单与具体数据权限一致。业务成功但发信失败可重试且不重复业务；已读状态无跨用户修改；通知目标撤回不泄露。相同测试数据的注册/活跃/无结果统计可复算，敏感搜索不保留原文；网络失败不自动下架；首页推荐撤稿立即隐藏。
