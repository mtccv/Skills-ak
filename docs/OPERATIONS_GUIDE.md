# 运营使用指南（Phase 12–13）

主题/Core 0.13.0，schema 1.9.0，33 张 Core 表。运营层复用已有账户、审核服务、通知 outbox、工作流事件、日聚合和首页配置，不建立新的用户、投稿、邮件或统计主存储。当前增量验证见 [Phase13报告](PHASE_13_REPORT.md)，原运营交付见 [Phase12报告](PHASE_12_REPORT.md)。

## 权限与入口

WordPress 原生后台 AI Skills Hub 增加运营概览、待处理工作台、用户运营、通知与邮件、数据分析和来源健康入口。管理员在数据库版本正常时取得新增 Capability；其他角色需要由站点管理员明确授予。角色名称不是授权依据。

| Capability | 用途 |
|---|---|
| `aish_view_operations` | 运营概览、统一工作台；仍逐项检查业务权限 |
| `aish_manage_accounts` | 必要账户汇总、暂停和恢复普通用户的业务资格 |
| `aish_manage_notifications` | 脱敏邮件队列、暂停、到期恢复、有限重试 |
| `aish_view_analytics` | 运营聚合数据、受抑制的搜索词汇总 |

既有投稿、更新建议、社区评价、举报、作者认领、仓库、AI 和发现管理权限继续独立生效。拥有运营概览权限不等于可以读取所有队列，更不意味着可以发布资源、授予管理员权限或读取密钥。

## 每日处理顺序

1. 查看运营概览的更新时间、UTC 范围、单位及数据状态。区分真实零值、未配置和暂不可用。
2. 在待处理工作台按类型、状态和分页查看待办；进入原业务详情核对具体内容及修订。投稿被接受只进入后续流程，认领通过也不授予编辑权限。
3. 批量操作必须显式选中记录、填写相应反馈并确认；每项通过原服务重新检查权限、状态和修订。冲突项刷新后重新审核，不能用重复操作绕过版本检查。
4. GitHub 异常先核对任务状态和来源证据。扫描不完整、请求失败或一次超时不是永久失效。处理记录仅说明某个来源快照已被核查，不批准 Skill 或清除历史风险。
5. 在邮件页检查队列和固定错误码。邮件传输受理不等于真实送达；业务处理已经成功时不得再次审核来“补发”。
6. 数据分析以界面口径为准；当前存量、窗口内事件和用户日是不同单位，不能混算转化率或月独立用户。

## 用户暂停与恢复

用户运营只修改已有业务账户状态及受控操作记录，不修改 WordPress 角色、密码、邮箱验证证明或任何内容审核状态。暂停采用既有 `suspended` 状态，因此同时触发现有登录和受限操作门禁。恢复仅针对本界面建立的暂停，按原先状态恢复；删除隔离、原有未知暂停和损坏的状态不能在这里解除。

必须记录原因、操作者、时间及恢复条件。自身账户、管理员、原生编辑人员及持有管理权限的账户受保护；普通运营人员不得以此锁住站点管理员。暂停用户的公开互动按原查询门禁立即失效；恢复不会把拒绝、隐藏或撤回的内容改为批准。界面显示的收藏、评价、投稿是该账户的必要数量汇总，不暴露私人正文。

用户导出和删除继续使用现有 WordPress 隐私流程与身份绑定的清理服务。不得另建可通过用户 ID 下载别人数据的接口。内部暂停说明不会通过普通通知或前台公开；审核事件遵守保留期和匿名化流程。

## 来源健康

来源页区分仓库配置、采集任务和单个来源快照。可核对状态、路径、SHA 和原采集证据，并追加受控原因的处理记录。快照变更后旧处理标记不代表新内容已处理。重试每批最多 10 个既有仓库，使用现有异步采集队列、频率限制和重复任务保护；暂停或归档仓库不会被运营操作自动启用。

不会执行 Skill 脚本、任意访问输入 URL、自动删除内容、覆盖译文或撤销作者关系。AI 失败和不确定任务只展示原处理入口，不自动恢复暂停的 AI，也不自动重新调用收费 API。

## 首页运营

入口为 **AI Skills Hub → 发现与首页配置**，需要既有 `aish_manage_discovery` 权限。继续使用 Phase 11 的同一个 `aish_discovery_settings` 草稿/发布选项，不新增构建器或数据库表。每种语言仍有 10 个固定模块；展开模块后分别维护显示、顺序、数量、标题和公开说明。自然排行榜使用原真实查询，不能手工改分数、计数或替换为指定资源。

| 模块 | 可选来源 |
|---|---|
| 编辑精选 `collections` | 自动列出已发布集合；手动选择已有集合 ID；手动选择公开 Skill ID |
| 场景 `use_cases` | 自动列出已发布场景；手动选择已有场景 ID |
| 其他模块 | 原固定查询，不接受手动插入资源 |

手动选择最多 12 个不同 ID，按逗号输入顺序展示，数量设置为 1–12；ID 继续使用稳定内部身份，不因中英文不同而创建新关系。自动模式必须清空手选 ID。手选必须填写**公开推荐理由**，前台明确标识“人工精选 · 非自然排行”；不要将内部备注、举报内容或邮箱填入此字段。专题管理页可查询集合/场景 ID，Skill ID 沿用现有资源管理页及公开资源 URL。

模块时间填写 UTC `YYYY-MM-DD HH:MM:SS`：开始时间包含边界、结束时间不包含边界，空值分别表示立即开始或无期限。到期模块在每次页面查询时停止显示，不依赖 Cron 及时执行。后台分别检查草稿与当前发布配置，提示尚未生效、7 天内到期、已经过期，以及被下架、缺少当前语言译文或没有公开资源的手选内容。启用的过期模块和不可用手选项会阻止发布；可修正内容、调整时间或关闭模块后重试。专题自身仍必须已发布且至少有一个当前语言公开 Skill；未来排期不放宽这一条件。

操作顺序：**保存草稿 → 打开中文或英文私有预览 → 处理提示 → 勾选确认并发布配置**。预览只显示已保存的当前修订，使用现有首页 SSR 和当前 UTC 的公开条件；未来才生效的模块、未审核 Skill 和缺译内容不会被预览绕过。平台专题描述仍沿用已经发布的平台配置，预览只切换首页模块配置。预览必须具备管理权限、当前会话 Nonce 和完全一致的草稿修订；权限/Nonce 不符返回 403，草稿已变化返回 409，重新从后台打开即可。响应为 `private, no-store`、`noindex`，不输出 Canonical 或 hreflang，不应分享预览链接。

配置保存采用原 MySQL 命名锁、事务及修订比较；并发修改会拒绝旧修订，要求重新载入。保存草稿和发布均在同一事务追加 `workflow_events`，审计失败时配置也回滚。后台展示最近 20 条操作、修订、操作者 ID、UTC 和内容指纹；默认保留 365 天，不为旧版本伪造历史。没有任意 HTML/JavaScript 输入、真实统计覆盖或付费排序入口。

保存后清除原生 options 缓存；公开内容投影只在单次请求内复用，不持久缓存旧审核结果。下架、撤销审核或译文失效后，下一次请求重新执行公开门禁。首页本身发送 `private, no-store`；外部 CDN/页面缓存必须遵守该响应，不得缓存私有预览或登录页面。第三方缓存插件的实际兼容结果以阶段测试报告为准。

Phase 12 的既有工作流保持。Phase 13 增加的独立人工赞助不能成为付费排序，不新增营销群发或自动导入会员邮箱。完成后停在 Phase 13。


## Phase 13 商业预留的人工操作

新增“赞助展示”“赞助展示统计”“企业咨询”，分别需要 `aish_manage_sponsors`、`aish_view_commercial_metrics`、`aish_manage_enterprise`。默认仅管理员得到这些能力；原投稿审核员、仅运营概览或仅数据分析人员不会自动取得咨询正文或配置权限。“资源套装”沿用 `aish_manage_discovery`，复用现有集合。详情及统计口径见 [商业预留说明](COMMERCIAL_READINESS.md)。

1. **赞助**：先保存双语真实文案和合法素材，选择首页搜索下方或 Skill 详情底部；内部资源用 Skill ID，不能粘贴本站链接绕过公开条件。设置 UTC 生效/结束时间，核实来源与素材权利，填写审核原因并确认启用。全局开关与条目状态必须都允许展示。后台私有预览不产生公开 URL 或展示计数。
2. **套装**：先按原策展流程完成集合、对应语言和公开成员，再选择有限集合入口。没有内容或成员被下架时入口不展示；套装不声称拥有成员版权，不生成另一份 Skill 或商品。
3. **企业咨询**：先分别填写中文/英文实际服务说明再启用，对应 Contact 页面才显示企业说明和独立表单。待处理 → 处理中 → 关闭/归档仅记录人工处理状态；咨询不是订单，内部备注私有。普通 Contact 与会员投稿规则不变。导出/擦除通过已确认的 WordPress 原生隐私申请处理。
4. **指标**：后台选择 7/30 日窗口，注意包含今天尚未完整的 UTC 日。展示、点击、每日去重观测及实际收到的咨询分别显示；不是购买、收入或成交率。原观察同意不自动扩展到商业目的，关闭统计或未同意会造成明确的覆盖不足。

冲突时重新载入最新修订，核对内容后再操作，不连续盲重试。配置与审计同事务，失败不会只写入其中一半。关闭或到期在实际展示时检查，不依赖 Cron；公开门禁仍实时检查，不使用历史统计缓存作安全判断。

运营概览只在单次请求内复用权限与计数，批量统计替代逐行投影，没有新增跨请求缓存。真实 WordPress/MySQL 快照服务测量与相同数据集对照见 [性能报告](../PERFORMANCE_REPORT.md)；201→87 为服务 SQL 计数，不是整个后台 HTTP 页面的总查询数，也不是生产吞吐量承诺。
