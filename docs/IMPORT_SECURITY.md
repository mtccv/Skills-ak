# GitHub 采集安全说明

适用于 Phase 5 `Sources` 模块。外部仓库、文件名、SKILL.md、YAML 元数据以及其中的自然语言全部属于不可信数据，不能授权系统读密钥、访问任意 URL、调用后台接口或执行命令。Phase 6 的独立 AI 模块继续保持输入与系统指令隔离，其新增边界见 [AI_SECURITY.md](AI_SECURITY.md)；本轮开发仍未运行真实 AI API 验收。

## 网络与凭据

统一 `GitHubClient` 只构造 `https://api.github.com` 的仓库、分支、Git Commit、Tree、Blob REST 路径。输入仓库 URL 单独验证，文件不按外部 `download_url` 下载。生产使用 `wp_safe_remote_get`、TLS 校验、禁止重定向、15 秒超时及有界响应；请求关闭压缩，避免绕过响应限制。拒绝携带凭据的 URL、未知主机、端口、查询和片段。树路径只作逻辑路径，不写入本地文件系统。

Token 仅在服务器环境变量/常量读取，发送到固定 API 主机；后台和日志不包含 Token、原始认证头或原始 API 错误体。限流状态使用散列配置键缓存配额/时间，采用固定诊断代码。即使认证 Token 可读私有仓库，也必须通过公开可见性校验。每个远程工作步骤核对固定 GitHub Repository ID，拒绝地址被其他仓库替换；不自动追随仓库重命名。

## 解析与资源消耗

自包含的受限 YAML 解析器不调用反序列化对象、PHP YAML 扩展对象构造、`eval`、shell、依赖安装或外部服务。标签、锚点、别名、合并键、重复键、未知字段、类型混淆及复杂语法明确拒绝。UTF-8、控制字符、长度、字段和目录规则分别验证。Git Blob 内容同时校验大小、Base64 和真实 Git 对象 SHA。

树深度、条目、候选数量、HTTP/文件/状态体积、重试次数、租约和任务寿命均有上限。截断递归树重新分层遍历，不能拿部分清单做删除推断；非递归仍截断或超限时安全结束为不完整。单文件解析失败记录日志并继续其他候选，整个任务保留错误状态。

后台批量上限、每仓库活动任务唯一键、全局调度锁、事务与租约共同限制重复执行。持有旧租约的 worker 无权写回已取消或被重新领取的任务。源路径、ID、状态、排序/筛选来自验证值，数据访问使用既有参数化 DAL 与列白名单。

Phase 7 首批修复统一了旧 Repositories 与 Imports 的归档入口，归档同时关闭同步并取消队列，恢复不会继续旧租约。仓库人工改名先取得身份行锁再建立读取快照，避免等待期间刚提交的 Skill/任务绑定被旧快照遗漏。清单对账提交后的恢复保留原 Commit 和缺失计数，旧检查点不能抹掉对账证据；针对性测试使用事务/交错替身，真实 InnoDB 并发与故障恢复仍待 Final QA。

## 静态检查的含义

检查覆盖 License 声明与仓库 SPDX 信息、依赖/工具声明、脚本扩展名、网络连接、特权操作、可疑命令执行、密钥读取提示、Prompt Injection 提示、路径异常、超大文件及异常目录结构。检查范围是 **SKILL.md 文本和 Git Tree 元数据**，没有执行脚本、安装依赖或审计全部源文件。

结果是人工审核线索，不是恶意软件检测结论或绝对安全认证。没有匹配风险模式时仍为 `unknown`，不会自动标为安全或批准发布。License 声明即使存在也属于 `declared_unverified`；缺失、未知或冲突需要人工核实。恶意文本可能规避模式检查，因此批准前仍需核对真实来源、权限、许可证和使用步骤。

外部原文、元数据、路径和发现结果在后台按各自 HTML 上下文转义；不把远程 Markdown 的脚本/HTML直接渲染成活动内容。日志只保存固定事件描述与经过验证的关联路径，不保存任意响应体。来源内容只通过受权限保护的后台显示。

## 内容和审核边界

新采集 Skill 固定待审核，没有自动译文和公开路由资格。现有资源只追加来源快照和待处理通知，不改人工编辑的译文、slug、审核人、审核修订或发布状态。公开查询、SEO、Sitemap 继续使用既有发布及当前修订审核门禁。采集失败、来源缺失或风险变化不会直接删除已发布记录；管理员核实后可编辑、拒绝或归档。

同一仓库的不同路径拥有不同来源身份；疑似移动仅提示，不以名称或猜测合并稳定 ID。File SHA 与 Commit SHA 分别记录，版本保留来源快照。风险重检 Commit 另行注明，避免把旧原文版本冒充为新目录检查结果。

全部管理写操作检查 WordPress capability、POST 和 nonce；归档还有确认页面。后台查看也检查仓库管理权限。确认来源变更需要审核权限和最新来源指纹；“已处理”不改变审核或发布状态。批量关闭定期同步不能隐式恢复归档仓库。

## 数据保留与运维

schema 1.4.0 通过现有带锁版本迁移，保留原八张业务表，新增来源投影、任务、日志三张运营表，并为仓库/版本追加必要字段。无删除业务记录的升级或卸载逻辑。归档仓库取消活动任务，主题停用清除 Cron，均保留来源与历史。恢复使用前应核对 schema 状态及任务状态。

当前按每任务上限限制日志，尚未增加跨任务自动清理。Final QA 需验证长期任务/版本/日志容量与运维归档方案，不通过自动删除历史解决容量问题。

## Final QA 必验

- 真实公开 API 的认证/匿名、限流、二级限流、超时、重定向、仓库转私有/改名/替换与响应上限。
- 原始 1.0–1.3 数据安全升级到 1.4.0、重复迁移、失败恢复、现有八表内容/唯一键完整性。
- MySQL 事务与唯一约束、同时入队、租约过期、Cron 中断、归档与执行竞争、管理员编辑与采集竞争，以及死锁重试。
- 同 Commit 基线复用、部分写入后重放、截断/超限恢复、单文件失败阻止完整标记、完整清单才推断缺失。
- 原生后台权限/nonce/确认/XSS、私有原文不可公开读取，待审核资源不进入前台搜索或 Sitemap。
- WordPress Cron 的真实触发、低流量/禁用 Cron、PHP 运行超时、主题停用/重启恢复和队列吞吐。
- Phases 0–4 回归及 WPML、SEO 插件、浏览器与端到端验收。

本轮隔离模拟检查和 PHP 语法通过不能代替上述真实运行验证，尚未执行的项目不能报告为通过。


## Phase 7 第二轮加固

旧版本只在固定 Commit/Tree/Blob 身份及原文均验证后补齐空来源元数据；同 HEAD 的增量基线也检查 present 来源绑定，避免跳过必要核验。不修改已知身份或猜测其他 Commit，人工译文、稳定 ID、slug 和审核状态不受采集写入影响。任务/仓库检查点状态原子一致，第五次连续租约过期结束任务。

原生 mysqli 事务和整个 Cron 锁作用域在检测断线时阻止 wpdb 重连重放；回滚失败隔离连接。未知 COMMIT 可能已经提交，已发送的 GitHub 请求也不能撤回，不能将隔离模型解释为真实数据库并发证明。完整发现、边界和未执行项目见 [第二轮报告](PHASE_7_ROUND_2.md)。
